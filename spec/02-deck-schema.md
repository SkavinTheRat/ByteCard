# 题库 JSON 规格（`assets/data/decks.json`）

> 这份文件是 App 的「单词书」。首版由 Codex 生成种子内容，之后用户可以替换/扩充。
> 结构固定，改结构必须同步改 `src/db/seed.ts`。

## 1. 顶层结构

```jsonc
{
  "version": 1,                    // 题库版本，每次增删改都要 +1（App 端靠它判断要不要同步）
  "removed": [],                   // 墓碑列表：被下架的卡片 id，App 端据此执行 DELETE
  "minAppVersion": "1.0.0",        // 可选，仅构建期提醒，运行时不做拦截
  "decks": [ /* 学科包，6 个 */ ],
  "cards": [ /* 知识卡，约 100 张 */ ]
}
```

`removed` 的作用见 `spec/01-data-model.md` 4.1 节：App 端只会 INSERT 和 UPDATE，
**从 JSON 里删掉一行，老设备上那张卡不会消失**，必须靠墓碑显式删除。

## 2. decks

```jsonc
{
  "id": "ds",                      // 短 id，英文小写，用作外键
  "name": "数据结构",               // 中文名
  "code": "408-DS",                // 显示用编号
  "description": "线性表、树、图、排序与查找",
  "accent": "#22D3EE",             // 主题色，必须取自 spec/03-design-tokens.md
  "sortOrder": 1
}
```

**首版必须包含这 6 个包（顺序即 sortOrder）：**

| id | name | code | accent |
| --- | --- | --- | --- |
| `ds` | 数据结构 | 408-DS | `#22D3EE` |
| `co` | 计算机组成原理 | 408-CO | `#A78BFA` |
| `os` | 操作系统 | 408-OS | `#34D399` |
| `cn` | 计算机网络 | 408-CN | `#FBBF24` |
| `ai` | 人工智能 | AI-BASE | `#F472B6` |
| `agent` | 智能体 | AI-AGENT | `#60A5FA` |

## 3. cards

```jsonc
{
  "id": "ds-001",                  // 全局唯一，建议 `${deckId}-${三位序号}`
  "deckId": "ds",
  "type": "single",                // single | multi | fill | judge
  "question": "在长度为 n 的顺序表中删除第 i 个元素（1≤i≤n），平均需要移动多少个元素？",
  "code": null,                    // 可选：需要展示的代码/公式片段
  "options": ["(n-1)/2", "n/2", "(n-i)/2", "n-i"],
  "answer": { "index": 0 },
  "explain": "删除第 i 个元素要把它后面的 n-i 个元素前移；对所有 i 求和取平均得 (n-1)/2。选 B 是把「删除」和「插入」的移动次数搞混了。",
  "tags": ["线性表", "时间复杂度"],
  "difficulty": 2
}
```

### 四种卡型的字段规则

| 字段 | `single`（单选） | `multi`（多选） | `fill`（填空） |
| --- | --- | --- | --- |
| `options` | 必填，2~4 项 | 必填，3~5 项 | 必须为 `null` |
| `answer` | `{ "index": 0 }`（0 基） | `{ "indices": [0, 2] }` | `{ "accept": ["O(logn)", "O(log n)"], "hint": "用大 O 表示" }` |
| 判分 | 严格相等 | **完全一致**才算对；部分正确 quality=3 | 归一化后匹配 `accept` 任一项 |

### `fill` 的答案匹配规则（实现要点）

必须做归一化，否则用户体验很差：

1. 去首尾空白；全角转半角；英文转小写。
2. 去掉所有空格（`O(log n)` 与 `O(logn)` 视为同一答案）。
3. 去掉常见标点差异：`（）`→`()`、`，`→`,`、`；`→`;`。
4. 数字/符号同义：`×`→`*`、`÷`→`/`、`≤`→`<=`、`≥`→`>=`、`→`→`->`。
5. 命中 `accept` 中任一项即判对；未命中但**编辑距离 ≤ 1**（`src/utils/levenshtein.ts`）时判为「接近正确」，
   quality=3 并提示「答案基本正确，标准写法是：xxx」。这条能显著减少因为输入法/写法差异造成的挫败感。

## 4. 题型是开放集合（可扩展）

`type` **不是固定枚举**，它是 `src/cards` 注册表里的一个 key（见 `spec/04` 第 1 节）。
首版内置 3 种，阶段 10 通过注册表加入第 4 种，以后还可以继续加。

| type | 状态 | 字段约定 | 典型用途 |
| --- | --- | --- | --- |
| `single` | 首版 | `options` + `answer.index` | 概念辨析、计算选择 |
| `multi` | 首版 | `options` + `answer.indices` | 「以下哪些正确」 |
| `fill` | 首版 | `options: null` + `answer.accept` | 术语、公式、复杂度填空 |
| `judge` | 阶段 10 | `options: null` + `answer.value: boolean` | 快速判断对错，通勤场景 |
| `image` | 待定 | `payload.image` + `options` + `answer.index` | 图形联想（成本在画图） |
| `code` | 待定 | `payload.code` + `answer.accept` | 代码补全 |

### 4.1 `judge` 的字段规则

```jsonc
{
  "id": "ds-101", "deckId": "ds", "type": "judge",
  "question": "在单链表中，删除已知结点 p 的后继结点，时间复杂度是 O(1)。",
  "code": null,
  "options": null,
  "answer": { "value": true },
  "explain": "……", "tags": ["链表"], "difficulty": 2
}
```

- `answer.value` 必须是**布尔值**，不要写成 `"正确"` / `1`。
- `options` 必须为 `null`（UI 是两个大按钮，不是选项列表）。
- 题干里**不要**再带「判断对错：」这种前缀，UI 本身已经表达了。

### 4.2 `payload` 字段的使用规则

- 新题型专属字段**一律放 `payload`**，不许往 `options` / `answer` 里塞自定义结构
  （老版本 App 会对这两个字段直接 `JSON.parse`，格式一变就崩）。
- `payload` 缺省为 `{}`，不是 `null`。
- 老三种题型（`single`/`multi`/`fill`/`judge`）的 `payload` 保持 `{}`，不要用来存个性化数据
  （缓存类信息走 `ai_explain` 或单独的列）。

### 4.3 文件里要不要写 `minAppVersion`

`decks.json` 顶层加一个可选字段：

```jsonc
{ "version": 3, "minAppVersion": "1.0.0", "decks": [...], "cards": [...] }
```

用途：阶段 8 生产线如果生成了某个新题型的卡，而你装的是旧包，App 读到这些卡会走
`UnsupportedCard` 降级（`spec/04` 1.6）。`minAppVersion` 只是给**构建期**的提醒，
运行时不强制拦截——**不要做成「版本不够就拒绝启动」**，那会让用户彻底用不了。

## 5. 内容质量标准（Codex 生成种子题库时必须遵守）

这是整个 App 的**内容底线**，比代码质量更影响使用体验：

1. **题干自包含**：不出现「如上图」「前文提到的」这类依赖上下文的表述。卡片是随机出现的。
2. **干扰项必须是「像错的」**：错误选项要来自同类知识的常见混淆点，不能是明显荒谬的选项。
   反例：问时间复杂度，选项给「红色」「很快」。正例：`O(n)` / `O(nlogn)` / `O(logn)` / `O(n²)`。
3. **单选必有唯一最优解**，多选的正确项数量为 2~3 个且不固定。
4. **解析写三段式**（2~4 句，控制在 80~150 字）：
   - ① 结论 / 正确答案的依据；
   - ② 为什么其他选项错（点出具体混淆点）；
   - ③ 一句可迁移的口诀或考点提醒（可选）。
5. **`code` 字段**只用于真正需要看代码/伪代码/公式的卡（如递归、进程调度、TCP 报文段结构），
   其余留 `null`。代码片段单行不超过 40 字符，超过要手动换行。
6. **`difficulty`**：1 = 概念记忆题；2 = 需要一点推理；3 = 综合计算/易错陷阱。三档比例大致 4:4:2。
7. **`tags`** 1~3 个，复用已有标签，不要造同义标签（如「时间复杂度」和「复杂度」只留前者）。

## 7. 生成时的自检

生成完 JSON 后，Codex 必须自己跑一遍校验（可以写个临时脚本，也可以人工核对）：

- [ ] 所有 `id` 唯一，`deckId` 都存在
- [ ] `single` 的 `answer.index` 在 `options` 范围内
- [ ] `multi` 的 `indices` 至少 2 个且不重复
- [ ] `fill` 的 `options` 为 `null` 且 `accept` 非空
- [ ] 没有 `explain` 少于 40 字
- [ ] 每个 deck 的卡片数达到配额
- [ ] JSON 能被 `JSON.parse` 解析（不能有注释、不能有尾逗号）
